# B 题框架设计改进建议

本文针对同学提供的 `plan/framework-design.md`，总结框架设计层面的改进建议，不涉及开发进度安排。

## 一、总体评价

现有框架的模块划分和主流程合理，可以保留日志解析、代码索引、根因定位、补丁生成、分层验证和指标记录六个模块。

需要重点强化的是：**定位结论的证据、正确修复的行为约束、验证失败后的分类反馈，以及实验结果的可追溯性。**框架应证明修复有效，而不只是证明流程执行完毕。

## 二、七项改进建议

### 1. 规则提供候选，依据证据决定是否调用大模型

当前“规则优先、LLM 兜底”的方向可以保留，但规则命中不等于根因正确。例如，`list[i].name` 访问失败，可能由索引越界、数组空元素或上游加载失败导致。

规则应输出以下内容：

- 候选根因位置。
- 支持该判断的日志和源码证据。
- 尚未确认的假设。
- 需要继续读取的代码。

只有证据充分且满足明确退出条件的简单案例，才直接输出定位结果；其他情况继续检索或调用大模型。初期的置信度分数应注明为启发式评分，不能解释为真实正确概率。

### 2. 采用按需代码检索，控制静态分析范围

不必在第一版实现完整的 ArkTS 跨文件数据流分析。建议逐步扩展上下文：

```text
堆栈对应语句
    ↓
所在函数和相关类字段
    ↓
直接调用者、被调用者
    ↓
参数、变量和数据定义位置
```

定位模块按需申请更多上下文，并限制文件数、代码量或 Token。源码映射结果应区分“唯一匹配、多候选、未找到”，避免同名文件被错误匹配。

### 3. 定位输出支持多个位置，并绑定原始源码版本

根因可能涉及上游数据产生位置、下游校验遗漏位置和最终崩溃位置，不能只用一个文件和行号表达。

建议定位结果包含：

| 字段 | 含义 |
|---|---|
| `crash_location` | 异常暴露位置 |
| `root_cause_locations` | 根因位置集合，支持代码范围 |
| `evidence` | 日志、源码及调用关系证据 |
| `assumptions` | 尚未证实的推断 |

每次运行应记录原始源码版本或哈希。定位评分始终以原始代码为基准，避免补丁插入、删除代码后造成行号偏移。

### 4. 补丁生成前明确修复目标和行为约束

将“根因 → 补丁”调整为“根因 → 修复目标与约束 → 补丁”，防止模型只消除异常而破坏业务。

每次修复应明确：

```text
触发条件：什么输入或操作导致故障？
正确行为：该情况下应用应该如何处理？
保持条件：正常输入下哪些行为不能改变？
验证方法：通过什么测试证明以上要求？
```

例如，拖拽到“添加”格时应忽略、调整位置还是允许追加，需要结合业务语义判断。

补丁审查应检查行为，而非机械禁止语法。`try/catch` 和可选链可以合理使用；应拒绝的是吞掉错误、删除功能、无条件返回假结果等掩盖问题的修改。

### 5. 验证失败后按原因返回对应模块

不应把所有失败都反馈给补丁生成模块。

| 失败原因 | 反馈方向 |
|---|---|
| 补丁无法应用、编译错误 | 补丁生成 |
| 原故障仍存在 | 根因定位或补丁生成 |
| 出现功能回归 | 修复约束与补丁生成 |
| 设备、签名、环境或测试前置条件异常 | 验证环境，标记阻塞 |
| 定位证据不足 | 扩展日志或代码上下文 |

保留每次尝试的记录，失败补丁应回滚到明确的基准版本，避免多轮修改无意叠加。共同限制候选补丁数量、重试次数、总调用次数和总时间，防止预算失控。

### 6. 验证采用多状态，区分局部通过和完整成功

将 `VerifyResult.passed` 布尔值扩展为状态字段：

- `PASS`：执行完成，满足该层要求。
- `FAIL`：执行完成，发现不符合要求。
- `BLOCKED`：由于环境或前置条件无法执行，需要记录原因。
- `SKIPPED`：该层不适用或按明确规则跳过，需要记录原因。

保留现有四层验证，但明确证据边界：

| 层级 | 能证明什么 | 不能单独证明什么 |
|---|---|---|
| V0 补丁检查 | 修改可应用，满足基本约束 | ArkTS 工程可编译 |
| V1 Node 局部测试 | 抽取逻辑在指定输入下符合预期 | 鸿蒙运行行为正确 |
| V2 工程编译 | 工程通过对应工具链检查 | 运行稳定、功能正确 |
| V3 设备测试 | 指定操作与回归场景通过 | 所有场景均无问题 |

完整修复成功应以 V2、V3 的证据为核心。V1 不适用时可以跳过；设备阻塞时应报告“尚未完成运行验证”。

设备侧交接需绑定 `run_id`、源码哈希、补丁哈希、工具版本和测试版本，避免验证了错误构建产物或复用旧结果。

### 7. 加强评测隔离，明确指标口径

评测隔离建议采用允许清单，而非仅删除已知答案目录：诊断端只获得指定源码和日志；测试脚本与标准答案保留在独立验证端。测试输出反馈给模型前，需要过滤故障答案字段。

指标定义建议如下：

| 指标 | 统计口径 |
|---|---|
| 首次通过率 | 第一个候选补丁通过完整验证的比例 |
| 最终成功率 | 预算内至少一个补丁通过完整验证的比例 |
| 定位准确率 | 对照经核验的根因位置集合，分别统计精确位置、函数和文件命中 |
| 资源消耗 | 计入全部失败调用、候选补丁和重试 |
| 阻塞案例 | 单独列出数量与原因，并公开各指标分母，避免静默排除 |

## 三、建议的整体流程

```text
输入与版本固定
    ↓
日志解析＋按需代码检索
    ↓
规则提出候选＋证据驱动定位
    ↓
明确修复目标和行为约束
    ↓
生成补丁并审查
    ↓
分层验证
    ├─ 成功：保存补丁、验证证据与指标
    ├─ 失败：分类反馈，返回对应模块
    └─ 阻塞：保存状态与原因
```

## 四、优先修改顺序

1. 补充修复目标和行为约束。
2. 将统一重试改为按失败原因分类反馈。
3. 扩展验证状态，明确完整成功的判定条件。
4. 绑定源码、补丁、构建和验证结果的版本信息。
5. 完善候选证据、按需检索与评测隔离。

以上改进保留原框架的主体结构，重点使自动修复过程具备明确的决策依据、可靠的反馈机制和可复核的结果。
