# 定位规则库

实现位置：`src/dfx_repair/locate/rules/`。规则只提出候选，每条都附 `assumptions`，从不宣称已确认根因。

## 1. 预处理

| 步骤 | 做法 | 失败时 |
|---|---|---|
| 解码 | 按 BOM 识别 UTF-8 / UTF-16 | — |
| 栈帧提取 | 取第一个业务帧（排除系统库与框架路径），去掉设备前缀与 `file:` | 无业务帧 → `UNRESOLVED` |
| 路径映射 | 栈帧路径按后缀段匹配 `app/` 内文件 | 多个同名文件 → `UNRESOLVED`，候选放入 `unresolved_candidates` |
| 行号对齐 | 在日志行附近 ±8 行内找能产生该错误消息的表达式（如 `Cannot read property 'x'` 对应 `.x`），唯一时对齐 | 行号越界或候选不唯一 → 不对齐，保留原行并记录 |

## 2. 规则

### R-BOUNDS-PARTIAL（不完整的边界检查）

- 触发：错误为 `Cannot read property 'p' of undefined`，崩溃行读取 `arr[i].p`；同一函数中更早的 `if` 引用了 `arr.length` 和另一个下标，却没检查 `i`，且该 `if` 会提前退出。
- 输出：该 `if` 行，`role = missing_check`，分数 0.75。
- 示例：ComprehensiveTool1，崩溃行 83 → 根因 78（补 `|| index2 >= list.length`）。
- 前提：运行时 `i` 确实能达到 `arr.length`；排除稀疏数组、上游修改和其他守卫。

### R-BOUNDS-LOOP（循环边界多一）

- 触发：错误为越界类（`out-of-bounds`、`offset is outside the bounds` 等）；崩溃行唯一一次 `view.getXxx(offset)` 读取，`view = new DataView(buf)`；外层 `for (i = ...; i <= bound; ...)`，`bound` 由缓冲区长度除以步长得到，`offset` 依赖 `i` 与该步长；循环体内读取前没有修改 `i`。
- 输出：循环头，`role = off_by_one`，分数 0.7。
- 示例：AudioEditing1，崩溃行 58 → 根因 52（`<=` 应为 `<`）。
- 前提：最后一次迭代确实达到缓冲区末端；核对对齐、步长为正、声道布局。

### 回退

无规则触发时报对齐后的崩溃行，`status = CANDIDATE`。词法助手遮蔽字符串、注释与模板；模板内表达式无法分析时不报根因（`UNRESOLVED`）。

## 3. 根因判定原则（人工标注与复核用）

某行算"精确根因"，需同时满足：

1. 属于引入故障的改动；
2. 只改这一行就能消除崩溃，且不破坏正常功能。

只满足其一的行算"相关范围"。复核时回答四个问题：

1. 崩溃行的代码能否产生日志中的错误消息？
2. 哪几行像被改过？常见特征：为奇怪写法辩护的注释；绕远的写法（例如用 `ArrayList` 再用 `[]` 取值）；只服务一条特定路径的改动。
3. 只改答案行能修好吗？如果必须同时改别的行，那些行也算。
4. 有没有相邻行同样算错（条件判断与使用分两行写）？

## 4. LLM 分析纪律（冻结 prompt v4 摘要）

全文见 `src/dfx_repair/llm/prompts/localize_v4.txt`，修改须升版本号，且理由不得依赖具体案例。

1. 从崩溃行出发，说出失败的值，追到它被产生或最后赋值的地方（可跨文件）；读过产生处并确认无误后，才能报崩溃行。
2. 不要假设加空值或边界检查就修好了根因；判断无效状态是上游写错，还是合法状态没被处理。
3. 比较同类代码或数据；不一致只是线索，要说明它为何导致失败。
4. 注释不可信，除非代码或数据独立印证。
5. 多行语句中报含错误子表达式的那一行。
6. 不要编造需求来偏向某个候选。
7. 每条因果陈述都要有读过的代码行支撑。
